## 1. Purpose and Scope

This document defines the planned simulation scenarios for the Vessel Monitoring Gateway prototype.

The scenarios are intended to verify system behavior against applicable requirements, including safety-policy evaluation, alarm handling, simulated propulsion monitoring, navigation data processing, communication resilience, telemetry integrity, and API security.

The fixed scenario definitions below are retained from the baseline. This plan alone is not execution evidence; current scoped outcomes are recorded separately in formal-scenario-status.csv and linked case reviews.

The primary execution environment is software simulation. Controlled laboratory tests may be performed separately when suitable prototype hardware becomes available.

No scenario authorizes connection to operational vessel equipment.

## 3. Scenario Interpretation

### 3.1 Safety-Policy Simulation

SIM-001 through SIM-006 evaluate the intended behavior of configurable demonstration safety policies.

The specified hatch, vapor, water-level, and temperature conditions are simulated inputs or laboratory surrogates.

A virtual start decision does not activate a physical engine starter or ignition circuit.

A blocking condition shall be determined by the applicable demonstration configuration. No unverified operating rule shall be represented as a verified requirement for an actual vessel.

SIM-005 explicitly preserves configuration-driven behavior without assuming an operational high-water interlock.

### 3.2 Propulsion Simulation

SIM-007 uses the planned configurable N-engine model with a four-engine demonstration profile.

Engine RPM values are generated by the simulation provider.

The test does not represent measurements from operational propulsion equipment or verified engine diagnostics.

### 3.3 Navigation Simulation

SIM-008 and SIM-009 use NMEA 0183-style development sentences.

The expected behavior includes rejecting invalid input, preserving data quality, and transitioning navigation state according to configured data-age thresholds.

No operational navigation receiver, vessel position, or route is required.

### 3.4 Resilience and Recovery

SIM-010 through SIM-013 evaluate the planned handling of network outages, isolated sensor faults, concurrent failures, and subsequent recovery.

**SIM-011 coverage limitation:** The baseline scenario title is *Sensor bus fault*, but its specified stimulus is one invalid sensor while other sensors remain valid. Accordingly, its expected result evaluates **single-channel fault isolation**, not loss of an entire shared sensor bus. A common-bus outage that affects multiple channels would require a separately specified and mapped test before that failure mode could be claimed as covered. No such execution or coverage is claimed here.

The 60-second outage stimulus in SIM-010 is retained from the baseline scenario.

The system shall not be described as fault-tolerant or resilient in practice until the relevant tests have been executed and supporting evidence reviewed.

### 3.5 Telemetry and API Security

SIM-014 evaluates duplicate sample identity handling and conflicting duplicate rejection.

SIM-015 evaluates rejection of invalid or missing API authentication.

These scenarios require an implemented backend and must remain NOT_RUN until actual test execution is performed.

## 4. Evidence Required

Every executed test record must include:

- Requirement ID.
- Test ID.
- Source commit SHA.
- Firmware/backend version.
- Test environment.
- Test input or stimulus.
- Expected result.
- Actual result.
- PASS/FAIL outcome.
- Log or screenshot reference.
- Known limitations.

Where applicable, the record shall also identify the telemetry `source_mode`, relevant configuration, and observed quality or alarm state.

A test case may be marked PASS only after its expected behavior has been observed and documented through an actual execution.

A planned test case does not constitute verification evidence.

## 5. Simulation, Bench, and Physical Data Boundaries

| Source Mode | Intended Use |
|---|---|
| `simulation` | Software-generated test inputs and simulated system states |
| `bench_test` | Measurements produced in a controlled laboratory prototype environment |
| `physical` | Reserved for independently verified and authorized future physical interfaces |

Results from one source mode must not be presented as results from another.

Laboratory surrogate sensors must not be described as installed or approved marine protection equipment.

No real vessel, propulsion system, navigation equipment, electrical installation, or restricted operational data is required to execute the planned software simulation scenarios.
