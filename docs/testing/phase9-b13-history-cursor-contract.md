# Phase 9 Batch 13 — history cursor admission (scoped development)

All device-scoped history requests are routed through the existing Laravel API and authenticated prior to cursor validation. The cursor is opaque to clients, but is not an authentication token.

## Observed gap and change

B10 rejected base64/JSON decoding failures, but accepted otherwise-decodable cursors with missing, additional, or malformed query-order fields. Those values could reach `cursorPaginate` and turn user input into database errors. B13 validates the exact `(received_at, id)` ordering parameters and bounded types before invoking the read service. An invalid cursor is HTTP 422; service failures remain 500 or the narrowly recognized 503 connection-outage response. No replacement route, persistence schema change, or device authorization bypass is introduced.

For the existing MySQL `timestamp('received_at')` and unsigned BIGINT `id`, the accepted representation is `YYYY-MM-DD HH:MM:SS` and unsigned decimal integer 1..18446744073709551615. Pagination order stays `received_at DESC, id DESC`. An encoded cursor generated by Laravel is forwarded unchanged after validation. B9 and B10 fixture cursors are updated to match this actual query order.

Scope: UI-002, API-001, SEC-002, SYS-003, TST-001, TST-002. No database access, migration, production network, TLS, hardware flash, or formal SIM/SUP closure by this batch. The B13 feature suite runs only with mocked DeviceReadService and DeviceTokenAuthenticator; any actual DB attempt fails because DB_PORT=1 in the runner. CI's existing isolated MySQL job is independent and is not invoked by the batch runner.
